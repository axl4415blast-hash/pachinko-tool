# 機能移植手順：$ARGUMENTS

対象機能：**$ARGUMENTS**

このSkillは`引き継ぎログ_大東洋本店7機能移植計画.md`の「実装手順（1機能ごとに以下を繰り返す）」9項目をテンプレート化したものである。CLAUDE.mdの移植プレイブックに準拠する。

**必ず`CLAUDE.md`と`引き継ぎログ_大東洋本店7機能移植計画.md`を先に読んでから着手すること。** 特に`$ARGUMENTS`に対応するStepの「詳細仕様」「依存」「検証観点」セクションを確認する。

以下の9ステップを**順番に**、省略せず実行する。

---

## 1. プランモードで範囲を確定

- `grep -n`で`analysis_グラン本店.html`から、`$ARGUMENTS`に対応するHTML範囲（`id="page-$ARGUMENTS"`）・関数範囲・nav-item・`showPage`分岐の**実際の行番号**を確認する。
- ログ記載の行番号は執筆時点の参考値に過ぎない。必ず現物で再確認する（過去の実績でも作業が進むにつれ行番号はズレていった）。

## 2. バイト厳密コピー

- `sed -n '<開始>,<終了>p'`で行範囲を抽出する。
- 抽出前に**目視で範囲内を確認**し、無関係な既存コード（他機能の定義・共有定義など）が混入していないかチェックする（ZONE_CONFIGS巻き込まれ削除事故の教訓）。
- **理解して書き直すことは禁止**。要約・整形・変数名変更を含め、一切の書き換えをしない。
- コピー元・コピー先の改行コード（CRLF/LF）を`file`コマンド等で確認する。異なる場合は`tr -d '\r'`でLF正規化してから比較・貼り付けを行う。

## 3. sha256ハッシュで機械的な一致確認

- 抽出元ファイルと、大東洋本店への挿入後に同範囲を再抽出したファイルの両方で`sha256sum`を取り、完全一致を確認する。
- **目視diffで代替しない**。
- **`.migration-hashes/<機能名>.txt`に記録するsha256は、必ずCRLF→LF正規化してから計算する**（`check-migration-hashes.js`と同じ方式：`content.replace(/\r/g,'').split('\n')`で抽出後、`join('\n')`してからハッシュ化）。生の`sed`＋`sha256sum`（CRLF込みの生バイト）で計算した値を記録すると、コピー元・コピー先が実際には完全一致していても`check-migration-hashes.js`側の計算方式（LF正規化）とズレて常に不一致判定になる（Step1のdaymapで実際に踏んだ罠。挿入内容は正しかったが記録した参照ハッシュの計算方式が違っていた）。

## 4. 配線

- `nav-item`を追加する。
- `showPage('$ARGUMENTS', this)`ボタンを追加する。
- `renderPage`の分岐に`else if (id==='$ARGUMENTS') render<関数名>();`を追加する。

## 5. 構文・構造チェック

- `node --check`で構文確認する。
- HTML内`<div>`開閉バランスを確認する（差1が既定値）。
- `.claude/hooks/check-undefined-refs.js`で未定義参照が無いことを確認する。
- 埋め込みコアがある場合は`*_core.js`とdiffでバイト一致を確認する。

## 6. 合成データ検証

- 仕込んだシグナルと非仕込みとで、スコア・判定が明確に分離することを確認する。**例外が出ないだけでは合格にしない**。
- `$ARGUMENTS`がStep4（halltype）の場合：Bonferroni補正の効果を、補正なし版と比較して確認する。
- `$ARGUMENTS`がStep7（carryover）の場合：Mantel-Haenszel正規化と層別集計の効果を確認する。

## 7. 実データ経路の実地確認

- 実際にGASからデータを取得し、該当ページをブラウザ（PC Chrome）で開いて描画・コンソールエラー無しを確認する。
- `node --check`だけでは検出できない未定義参照バグ（大東洋本店移植のZONE_CONFIGS事故）があることを踏まえ、必ず実地で通す。

## 8. 報告・承認待ち（★ここで必ず停止する）

以下をまとめてブラスト（ユーザー）に提示する：

- `git diff --stat`
- grep残存確認（旧コードが残っていないか、大東洋固有コードを壊していないか）
- `node --check`の結果
- 実データ確認の結果（スクリーンショット・コンソールログなど）

**このステップで作業を止め、ブラストの明示的な承認を得るまで、絶対にコミットしない。** 承認前に`git add`/`git commit`を実行することは禁止。承認が得られてから初めて次のステップ（コミット）に進む。

## 9. push・PR反映確認

- 承認後、コミットしてpushする。
- CIがgreenであることを確認する。
- GitHub Pagesへの反映を`last-modified`ヘッダー等の一次情報で確認する（ステータス文字列だけを信じない。過去にビルド失敗を「ビルド中」と誤認した事故がある）。
- 5分以上「building」で停滞したら[githubstatus.com](https://www.githubstatus.com/)を確認し、必要なら失敗ジョブを再実行する。

作業用ブランチ（例：`daitoyo-7features`）上で作業し、`main`には直接コミットしない。7機能すべて完了・実機確認OKが出てからマージする。
